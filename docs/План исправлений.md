# План исправлений Soul-journey

Документ фиксирует согласованный план первого этапа стабилизации проекта. План составлен по результатам статического аудита репозитория и уточнений владельца проекта от 30 октября 2026 года.

## Цели этапа

1. Сохранить существующую архитектуру и игровой функционал.
2. Устранить риски потери сохранений.
3. Сделать безопасным первоначальное создание и использование учётной записи администратора.
4. Исправить обнаруженные ошибки игрового цикла.
5. Добавить базовые защитные механизмы для публичного запуска в будущем.

На этом этапе не переписываем проект, не меняем игровой баланс без отдельного согласования и не удаляем административную роль.

## Принцип работы с администратором

Администратор в игре обязателен. Роль администратора и возможность администрировать игру сохраняются.

При установке новой копии игры должен создаваться первоначальный администратор. Установщик или инструкция по развёртыванию должны требовать сменить первоначальный пароль при первом входе.

Требования к реализации:

- Не удалять механизм первоначального создания администратора.
- Не отключать административную панель и права администратора.
- Не оставлять общий известный пароль постоянным рабочим паролем.
- При первом входе первоначальный администратор должен быть принудительно направлен на смену пароля; до смены пароля доступ к остальным функциям администратора ограничивается.
- После успешной смены пароля флаг обязательной смены пароля снимается.
- При чистой установке временный пароль генерируется случайно и выводится в консоль сервера однократно при создании администратора; установщик должен сохранить его для первого входа. При необходимости временный пароль можно заранее задать через переменную окружения `SUPERUSER_PASSWORD`.
- Временный пароль не хранится в исходном коде и обязательно меняется при первом входе.
- Повторный запуск сервера не должен самовольно сбрасывать пароль администратора или повторно выдавать административные права: права назначаются при первичном создании аккаунта и не восстанавливаются автоматически после отзыва.
- Не хранить реальные секреты и рабочие пароли в репозитории.

## Этап 1. Безопасность и надёжность

### 1.1. Первоначальная настройка администратора

**Приоритет: P0**

- Сохранить обязательную учётную запись администратора.
- Реализовать обязательную смену первоначального пароля при первом входе.
- Проверить, что повторный запуск приложения не перезаписывает установленный пароль.
- Проверить, что обычный пользователь не может получить административные права через регистрацию или изменение клиентских данных.
- Описать процедуру первоначальной установки и восстановления доступа.

**Критерий готовности:** после чистой установки администратор существует, может войти с временными учётными данными, обязан задать новый пароль, а после этого повторный запуск не меняет его пароль и права.

### 1.2. Защита сохранений от повреждения

**Приоритет: P0**

Файл: `server/store.js`

- Разделить ситуации «файл базы отсутствует» и «существующий файл не удалось прочитать».
- При первом запуске, когда файла ещё нет, создавать пустую базу штатным способом.
- При повреждённом JSON или неверной структуре не подменять базу пустой базой автоматически.
- Перед отказом загрузки сохранять точную копию повреждённого файла рядом с `data.json` под уникальным именем `data.json.corrupt-...`.
- При невозможности прочитать существующий файл или проверить его метаданные возвращать понятную ошибку; сервер не должен продолжать работу с пустой базой.
- Записывать сохранения в уникальный временный файл, синхронизировать его через `fsync` и только затем атомарно заменять основной файл.
- При ошибке записи оставлять данные в памяти, не снимать флаг несохранённых изменений и повторять попытку; при неудачном штатном завершении возвращать ненулевой код.
- Сохранить совместимость с устаревшими сохранениями, в том числе с отсутствующими или `null`-полями, которые ранее допускались миграциями.

**Критерий готовности:** повреждённый файл сохраняется для восстановления, сервер явно отказывается загружать его, а запись не очищает флаг несохранённых изменений при ошибке.

**Реализация:** код находится в ветке `fix/store-corruption-safety`. Добавлены регрессионные тесты на чистый первый запуск, повреждённый JSON, неверную структуру, совместимость со старыми `null`-полями и удаление уже существующего файла во время работы. Команда запуска: `npm run test:store`. Синтаксис файлов проверен; выполнение набора тестов и запуск локального сервера ещё предстоят.

### 1.3. Согласованность кэша и файла базы

**Приоритет: P1**

Файл: `server/store.js`

- Закрепить модель одного владельца: только один процесс может одновременно работать с конкретным `data.json`. Для этого хранилище создаёт эксклюзивный файл блокировки `data.json.lock`; второй экземпляр сервера или сервисный скрипт получает понятную ошибку.
- Считать кэш в памяти единственным источником истины в течение жизни процесса. Файл читается при первоначальной загрузке и не подменяет кэш автоматически.
- Периодически проверять подпись файла (устройство, inode, размер и время изменения). Проверка нужна для обнаружения внешней записи, а не для автоматического перечитывания.
- При удалении или внешней замене/правке файла фиксировать конфликт, сохранять отдельный снимок кэша `data.json.memory-conflict-...` и отказываться перезаписывать изменённый файл.
- Перед каждой отложенной записью повторно проверять подпись файла, чтобы поймать конфликт, возникший после последнего чтения.
- Сервисные скрипты, которые меняют базу (`reset-password.js`), запускать только после остановки сервера.
- Обновить инструкции эксплуатации и игнорирование lock/temp/recovery-файлов Git.
- Не удалять автоматически оставшийся после аварии lock-файл: перед ручным удалением владелец должен проверить, что указанный PID больше не работает.

**Критерий готовности:** вторая копия процесса не может открыть базу; внешняя запись не перезатирается памятью сервера; несохранённое состояние получает отдельную копию; служебные изменения выполняются только при остановленном сервере.

### 1.4. Ошибка в игровом цикле при обработке топлива

**Приоритет: P0**

Файл: `server/index.js`

- Переместить создание массива `notifications` в начало обработки каждого аэропорта — до проверки и дозаправки по топливному контракту.
- Сохранить отдельный массив уведомлений для каждого аэропорта.
- Не менять условия разрыва контракта, цену топлива, объём дозаправки и экономические расчёты.
- Добавить регрессионный тест, который проверяет, что массив объявлен до первого обращения и до ветки `fresh.money <= 0`.
- Ошибки одного аэропорта и изоляция обработки остальных аэропортов остаются отдельной задачей пункта 1.6.

**Критерий готовности:** ветка разрыва топливного контракта не может обратиться к необъявленному `notifications`; порядок обработки и экономика топлива не меняются.

**Реализация:** исправление подготовлено в ветке `fix/fuel-contract-notifications-tdz`. Добавлен тест `server/tests/game-tick.test.js` и команда `npm run test:tick`; также добавлена общая команда `npm test`. Синтаксис изменённых JavaScript-файлов проверен; выполнение тестов и локальный запуск ещё предстоят.

### 1.5. Защита авторизации и входных данных

**Приоритет: P1**

- Добавить ограничение частоты попыток входа по аккаунту и IP с безопасной обработкой доверенных прокси.
- Ограничить частоту и объём регистрации.
- Проверить хеширование паролей, сравнение паролей и срок действия токенов.
- Проверить, что токен не попадает в логи и диагностические сообщения.
- Проверить валидацию чисел, идентификаторов, сумм, уровней и перечислений во всех финансовых и административных API.
- Проверить разграничение обычных и административных маршрутов.
- Проверить WebSocket-аутентификацию и закрытие соединений при истечении или отзыве токена.
- Не менять способ хранения сессий без отдельной проверки совместимости с текущим клиентом.

**Критерий готовности:** основные сценарии авторизации и финансовых API защищены серверными проверками, а некорректные запросы не меняют игровое состояние.

### 1.6. Устойчивость игрового цикла

**Приоритет: P1**

- Добавить централизованную обработку ошибок одного тика и одного аэропорта.
- Ошибка обработки одного аэропорта не должна незаметно прерывать весь цикл.
- Ошибки должны записываться в журнал с контекстом, достаточным для диагностики, но без паролей и токенов.
- Проверить поведение при ошибке сохранения данных.
- Проверить корректное завершение процесса и сохранение состояния при остановке сервера.

**Критерий готовности:** единичная ошибка игровой логики не приводит к необработанному завершению сервера или незаметной потере состояния.

## Этап 2. Автоматические тесты

После первичных исправлений добавить тестовую инфраструктуру и регрессионные проверки:

- Хранилище: пустая база, корректная база, повреждённая база, резервная копия, атомарная запись.
- Администратор: первичное создание, обязательная смена пароля, сохранение роли, повторный запуск.
- Авторизация: регистрация, вход, неверный пароль, ограничения частоты, права доступа.
- Строительство: стоимость, требования, апгрейды, снос и ограничения.
- Экономика: доходы, расходы, налоги, банк, долг и банкротство.
- Договоры и расписание: лимиты, конфликты, прибытия и вылеты.
- Игровой цикл: ошибки одного аэропорта, топливные сценарии и сохранение.

Тесты должны запускаться отдельной командой через `npm test` и не использовать рабочий файл `data.json`.

- Проверить пропускную способность ВПП, стоянок и терминалов.
- Проверить доступность сюжетных целей и вероятность раннего банкротства.
- Не менять баланс без результатов симуляции и согласования.

## Этап 4. Постепенное улучшение архитектуры

- Разделять `server/index.js` на маршруты и сервисы небольшими безопасными шагами.

- Не проводить полную перепись сервера или клиента.

## Этап 5. Синхронизация документации

- Обновить README и документы, содержащие устаревшие правила игрового времени.
- Сверить описания механик с текущим кодом.
- Отделить действующие механики от запланированных.

## Порядок выполнения

1. Согласовать и реализовать безопасную первоначальную настройку администратора.
2. Исправить загрузку и сохранение базы данных.
3. Исправить ошибку массива `notifications` в игровом цикле.
4. Добавить защиту авторизации и серверную валидацию.
5. Добавить обработку ошибок игрового цикла.
6. Добавить автоматические тесты для всех исправлений.
7. Только после этого переходить к расширению игровых механик.

## Правила безопасной разработки

- Перед изменениями фиксировать исходное состояние Git-коммитом или отдельной веткой.
- Не выполнять миграции реальных сохранений без резервной копии.
- Не удалять и не сбрасывать данные игроков.
- Не менять существующие игровые правила без согласования.
- Не заменять текущий стек: Node.js, Express, WebSocket и JavaScript остаются основой проекта.
- После каждой задачи запускать тесты и проверять diff.
- Все изменения вносить небольшими логическими порциями.

## Текущее состояние

На момент составления плана игра работает локально, сервер остановлен, реальных работающих серверных сохранений, требующих миграции в production, сейчас нет. Это позволяет спокойно подготовить и проверить исправления локально до следующего публичного запуска.

**Статус документа:** этап 1 завершён в `main` (PR #3–#10). Этап 2: PR #11–#16 добавили тесты чистых механик и HTTP API; PR #17 добавил сквозную проверку полного перехода из главы 1 во 2, принятия обычного договора, назначения строки и успешной постановки рейса в расписание, а также отказов на повторную ячейку и неверный слот. GitHub Actions на Node.js 22 подтвердил **57/57 тестов**. Интеграционный сценарий использует временные data/media каталоги, не записывает данные напрямую и оставляет проектные `data.json`/lock неизменными. Следующие задачи этапа 2 — налоговый цикл, погашение/просрочка кредита, банкротство и сохранность состояния после серии игровых тиков. Отдельно перед публичным запуском нужен аудит трёх dependency advisories из `npm ci` (1 moderate, 1 high, 1 critical).
